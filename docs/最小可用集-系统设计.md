# AI 数据分析助手 · 最小可用集设计（MVP）

本文是 `系统总体设计.md`（大系统，25 个阶段）的**严格子集**：阶段编号、目录路径、函数签名、端点路径、表名全部沿用大文档，一个都不改名。这样做的唯一目的：以后按大文档往后加阶段时，只做「新建文件 + 注册表加一行 + 编排层插调用」，已验收的代码一行都不用重写。

跑通本文的 7 段，就有「上传表格 → 中文提问 → 模型多步查数 → 结果表 + 结论 + 图表 → 网页可用」的完整闭环。

## 0. 怎么用这份文档

- 顺序：P0 → P1 → P2 → P3 → P13 → P4 → P5，共 7 段，每段一条验收命令，exit 0 才进下一段。
- 每段结束贴出真实输出。不贴等于没做。
- 「改动范围」写死的文件之外不许动；越界说明契约需要更新，回到大文档登记。
- 本文只写 MVP 需要的那部分契约；需要全集时看大文档第 4 节，两边不会冲突。

## 1. 范围

做：CSV/XLSX 上传与清洗、数据画像、SQL 查询与统计、异常检测、中文提问 → 多步工具调用 → SQL → 结果表 → 结构化结论、单页前端。

不做（对应大文档阶段）：SSE 流式(P17)、后台作业(P18)、缓存与多轮记忆(P10)、语义检索(P14)、多模型与回退(P9)、Skill(P6)、知识库(P7)、MCP(P8)、登录与公网部署(P11)、桌面安装包(P12)、代码沙箱与指标语义层(P15)、评测与可观测(P16)、报告导出(P19)、收藏与重导入(P20)、并发契约(P21)、多表关系(P22)、数据源(P23)、反馈与配额(P24)。

## 3. 冻结契约

### 3.1 内部接口签名（与大文档逐字一致）

```python
# app/db.py
def exec_sql(sql: str, limit: int = 5000, timeout_s: int = 10) -> dict
def register_table(dataset_id: str, df) -> str

# app/ingest.py
CLEAN_RULES: dict
def ingest_file(path, name: str) -> dict
    # {"dataset_id","table","rows","cols","profile","clean_log","table_version"}

# app/models.py
def list_models() -> list[dict]
def resolve(model_id: str | None) -> dict

# app/llm.py
def chat_json(system: str, user: str, schema: type, model_id: str | None = None) -> object
def chat_tools(messages: list[dict], tools: list[dict], model_id: str | None = None) -> dict

# app/tools.py
def register(name: str, fn, schema: dict, kind: str) -> None      # kind: read | write
def all_tools(allow: set[str] | None = None) -> list[dict]
def call(name: str, arguments: dict) -> dict

# app/agent.py
def run(question: str, session_id: str | None, dataset_id: str,
        model_id: str | None = None, max_steps: int = 6) -> "AgentResult"

# app/nlu.py
def to_sql(question: str, profile: dict, context: list[str]) -> str

# app/insight.py
def summarize(question: str, result: dict, profile: dict, prior: list[str]) -> "Insight"

# app/registry.py
CAPABILITIES: dict[str, str]
def get(name: str)
def status() -> dict[str, bool]
```

MVP 里有两处"形状"是刻意提前摆好的，成本几乎为零，但决定以后能不能少改代码：

- `llm.py` 内部就按 `models.resolve()` + provider 分发写，即使只实现 `openai_compatible` 一个分支。P9 加 `anthropic` 分支时不动调用方。
- `agent.run()` 的 `session_id` 可以为 None，`insight.summarize()` 的 `prior` 在 MVP 传空列表。P10 接记忆时签名不变。

### 3.2 HTTP API（MVP 子集，路径与大文档一致）

| 方法 | 路径 | 用途 | 阶段 |
|---|---|---|---|
| GET | /health | 存活检查 | P0 |
| GET | /capabilities | 各能力可用性 | P0 |
| POST | /datasets | 上传（multipart） | P1 |
| GET | /datasets | 数据集列表 | P1 |
| GET | /datasets/{id}/profile | 画像与清洗日志 | P1 |
| POST | /query | 直接执行 SQL | P2 |
| POST | /stats | 描述统计与异常 | P2 |
| POST | /ask | 提问（走 agent） | P3 起步，P13 接管 |
| GET | /tools | 已注册工具与白名单 | P13 |
| POST | /insight | 对结果表出结论 | P4 |
| GET | /settings/models | 可用模型 profile 列表：id、base_url、模型名、是否已配密钥（不回传密钥明文） | P5 |
| PUT | /settings/models | 新增或更新一个 profile（任意 OpenAI 兼容厂商）并写密钥到 `config/local.json`，返回同 GET | P5 |

`POST /ask` 请求与响应（与大文档 4.3 同一个形状，MVP 里 `cached` / `reused_sql` 恒为 false）：

```json
{"dataset_id": "d_7f3a", "question": "上月华东区销售额环比下降的产品有哪些"}
```
```json
{
  "task_id": "t_1042", "dataset_id": "d_7f3a",
  "sql": "SELECT product, sum(amount) ... GROUP BY 1 ORDER BY 2 LIMIT 50",
  "columns": ["product", "cur", "prev", "ratio"],
  "rows": [["A", 1200, 1500, -0.2]],
  "steps": [{"n": 1, "tool": "run_sql", "args_digest": "a1f3", "ms": 92, "rows": 12}],
  "insight": {
    "summary": "华东区 3 个产品环比下降，A 降幅最大 -20%",
    "findings": [{"title": "A 环比 -20%", "detail": "1500 -> 1200", "metric": "ratio", "direction": "down"}],
    "anomalies": [{"column": "ratio", "row_hint": "华东/A", "reason": "低于 IQR 下界"}],
    "suggestions": [{"action": "核查 A 的渠道库存", "rationale": "降幅集中在单渠道"}],
    "confidence": "medium",
    "caveats": ["未包含退货数据"]
  },
  "cached": false, "reused_sql": false, "degraded": []
}
```

`/query` 响应：`{"sql", "columns", "rows", "row_count", "truncated", "hint"}`（`hint` 只在被截断时非空）。

`/stats` 响应：`{"dataset_id", "rows", "table", "row_count", "truncated", "columns": [...], "anomalies": [...]}`。

`/ask` 响应：`{task_id, dataset_id, sql, columns, rows, row_count, truncated, steps, cached, reused_sql, degraded, message}`；降级时 `degraded` 非空、`sql` 为空串、`rows` 为空、`message` 给可读说明，HTTP 仍 200。

### 3.3 数据模型（SQLite，MVP 建这 5 张）

| 表 | 关键字段 |
|---|---|
| datasets | id, name, source_id, source_path, table_name, rows, cols, profile_json, clean_log, table_version, owner, created_at |
| tasks | id, dataset_id, session_id, kind, question, sql, status, degraded_json, error, created_at |
| agent_steps | id, task_id, n, tool, args_json, ok, ms, rows, error, created_at |
| trace_spans | id, task_id, name, model_id, tokens_in, tokens_out, cost, ms, ok, created_at |
| capability_log | id, capability, event(up/down/call/error), detail, created_at |

建表统一走 `store.ensure_tables()`，全部 `CREATE TABLE IF NOT EXISTS`。扩展阶段加新表时在同一函数里追加，幂等，不需要迁移脚本。

DuckDB：每个数据集一张 `ds_<dataset_id>`，只读连接执行 `exec_sql`。

### 3.4 LLM 契约

- 输出 `Insight`：`summary, findings[], anomalies[], suggestions[], confidence(low|medium|high), caveats[]`。
- 硬规则：结论里的数字必须能在结果表中找到；证据不足写 `caveats`；指代不明返回 `need_clarify` 而不是猜。
- 失败处理：重试 1 次 → 仍失败则 `insight` 置空、`degraded` 追加 `insight:contract`，HTTP 仍 200。
- prompt 写成模块级常量并带 `PROMPT_VERSION`（P10 加缓存时这个常量就是缓存键的一部分）。
- `config/models.json` MVP 只放一个 profile：

```json
{"default": "local",
 "models": [{"id": "local", "provider": "openai_compatible",
   "base_url": "https://api.deepseek.com/v1", "model": "deepseek-chat",
   "api_key_env": "LLM_API_KEY", "purpose": ["sql", "insight"]}]}
```

密钥与 profile 来源：**本地文件优先、环境变量兜底**，页面能配任意 OpenAI 兼容厂商——页面写入的 `config/local.json`（已 gitignore）里的 `models` 数组与 `models.json` 合并（同 id 以本地为准，于是 DeepSeek/Qwen/GLM/Ollama 只是换一条 profile），密钥按 profile 存在 `api_keys: {profile_id: key}`；本地没有就回落该 profile 声明的 `api_key_env` 环境变量，再兜底通用 `LLM_API_KEY`。读取发生在调用时而不是 import 时，所以页面保存完立刻生效，不用重启服务、也不用 `setx`。P9 加厂商走的就是这同一个形状。

### 3.5 工具契约（MVP 注册 3 个）

`config/tools.json` 控制白名单、超时与步数预算。

| 工具 | kind | 作用 |
|---|---|---|
| run_sql | read | 执行单条 SELECT |
| describe_stats | read | 描述统计 |
| detect_anomalies | read | IQR/z-score 异常 |

硬规则：`max_steps=6`；每步独立超时；单步结果超过 200 行只回传摘要与列名（全表留在服务端，下一步用 `run_sql` 再取）；越权调用记 `capability_log` 并返回拒绝说明；步数耗尽返回已完成步骤与阶段性结论，不报错。

P6/P7/P8/P15/P19 加能力时，都是往这张表里 `register()` 新工具，循环本身不动。

## 5. 扩展契约（这是"能一路长成大系统"的全部秘密）

往后加任何阶段，只允许做三件事：

1. **新建文件**实现新能力（provider、模块），按大文档给的路径命名。
2. **注册表加一行**：`registry.py` 的 `CAPABILITIES`，或在 `tools.py` 里 `register()` 一个新工具。
3. **编排层插调用**：只在 `main.py` 的编排位置插入，不进 `nlu.py` / `agent.py` 的内部逻辑。

配套的三条禁令：
- 禁止改已验收阶段的函数体（要改契约就先回到大文档登记，再同步改验收命令）。
- 禁止让下层 import 上层；`providers/*` 只被 `registry.py` 惰性 import。
- 禁止为"以后可能用到"提前加抽象层；需要新形状时按第 6 节判断，不靠感觉。

为什么这三件事够用：模型调用全在 `llm.py` 一个出口，工具全在 `tools.py` 一张表，能力全在 `registry.py` 一个字典，落盘全在 `db.py` / `store.py` / `ingest.py`。这四处是唯一的改动面，别的地方都是叶子。
